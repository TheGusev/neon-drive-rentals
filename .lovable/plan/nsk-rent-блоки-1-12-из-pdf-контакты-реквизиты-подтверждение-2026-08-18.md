## Шаг 2 (БЛОК 3). Админ: автопарк на реальной БД

`getCarsAdmin`, `createCar`, `updateCar`, `updateCarStatus`, `deleteCar`. Статусы в БД остаются `available/busy/wash/maintenance`, в интерфейсе — Свободен/Занят/Мойка/ТО. Загрузка фото авто server function'ом в `/public/assets/cars/`. Визуал и фильтры не меняются.

## Шаг 3 (БЛОК 4). Админ: брони

`getBookingsAdmin(filters)` с join на cars и clients, `updateBookingStatus` со статусами `pending/confirmed/active/completed/cancelled`. При `confirmed`/`active` авто уходит в `busy`, при `completed`/`cancelled` возвращается в `available` (если нет других активных броней).

## Шаг 4 (БЛОК 5). Админ: клиенты

`getClientsAdmin` с количеством броней и суммой платежей, `toggleClientBlock` для чёрного списка.

## Шаг 5 (БЛОК 6). Админ: финансы

Платежи из таблицы `payments` (join bookings/clients), KPI из реальных данных, `exportPaymentsCsv(dateFrom, dateTo)` через уже установленный xlsx.

## Шаг 6 (БЛОК 7). Публичное бронирование → запись в БД

Календарь занятости считает пересечения по реальным броням: `confirmed`/`active` блокируют даты, `pending` подсвечивается отдельно как «предварительно забронировано». Форма на `/booking/:carId`: клиент ищется по телефону в `clients` (или создаётся), бронь создаётся со статусом `pending` и рассчитанной суммой, редирект на `/payment/:bookingId` с реальным id.

## Шаг 7 (БЛОК 8). SMS-коды (OTP)

Таблица `otp_codes`: `sendOtp(phone)` — 6-значный код, хеш, срок 5 минут, `verifyOtp(phone, code)` — блокировка после 5 неверных попыток. Провайдер SMSC.ru через `SMS_API_KEY`/`SMS_SENDER`. Пока ключа нет — код не уходит по SMS, а показывается в dev-режиме, логика проверки настоящая.

## Шаг 8 (БЛОК 9). Договор: PDF и подпись

Миграция `003_add_signature.sql` (`signed_at`, `signature_ip`, опциональный `specs.vin`). `signContract(bookingId, code)`: проверка OTP → бронь `confirmed` → генерация PDF (без нативных зависимостей) в `storage/contracts/{bookingId}.pdf`, кнопка «Скачать договор PDF» стримит файл. Визуал не меняем.

## Шаг 9 (БЛОК 10). ЮKassa

`createPayment(bookingId)` → API v3 с Basic Auth из `.env`, запись в `payments` (`provider='yookassa'`, статус `pending`), редирект на `confirmation_url`. Вебхук `/api/public/webhooks/yookassa` на `payment.succeeded`/`payment.canceled` с проверкой IP-диапазонов ЮKassa. Без ключей — режим-заглушка: платёж имитируется, статусы в БД проставляются так же.

## Шаг 10 (БЛОК 11). Кабинет клиента: вход по телефону

Вход через OTP, сессия-cookie `role='client'`, на `/profile` — текущая аренда, история броней клиента, документы-заглушка. Визуал не меняем.

## Шаг 11 (БЛОК 12). Вход через Яндекс ID

`/api/auth/yandex/start` и `/api/auth/yandex/callback`, обмен кода на токен, профиль через login.yandex.ru/info, привязка/создание клиента, та же сессия. Без `YANDEX_CLIENT_ID` кнопка скрыта. Оба способа входа работают параллельно.

## Технические детали

- Статусы БД не переименовываем: маппинг в `carsRepo.server.ts` / `bookingsRepo.server.ts` (`available↔free`, `wash↔washing`), в bookings убираем `paid` в пользу `confirmed`.
- Все секреты (`DATABASE_URL`, `SMS_API_KEY`, `YOOKASSA_*`, `YANDEX_*`) читаются в рантайме внутри хендлеров, в сборку не попадают.
- Новые server functions — тонкие обёртки, вся логика в `*.server.ts`.
