# Почему rentsib.ru не обновляется

## Что проверено сейчас

- `https://rentsib.ru/` отвечает 200 (nginx), но отдаёт **старую сборку**:
  - заголовок «… | RentSib» (бренд до переименования в NSK-RENT),
  - `og:url` = `https://neon-drive-rental.lovable.app`,
  - в `sitemap.xml` все `<loc>` тоже `neon-drive-rental.lovable.app`,
  - в описании ещё есть «Доставка в Толмачёво», хотя доставку мы удалили,
  - `/robots.txt` отвечает 404 — маршрут, добавленный позже, на сервере отсутствует.
- В текущем коде: `SITE_URL = https://nsk-rent.ru`, бренд NSK-RENT, единый пункт выдачи «Доватора, 11», есть маршрут `robots.txt`.
- В репозитории **нет** GitHub Actions (`.github/workflows` отсутствует) — автоматической сборки/деплоя из репозитория нет.

Вывод: код в Lovable свежий, а на сервере лежит сборка примерно от 6 августа. Значит рвётся звено между репозиторием и сервером, а не сам код.

## Где именно может рваться цепочка (проверяем по порядку)

1. **Lovable → GitHub.** Если синхронизация с GitHub отключилась/переподключена к другому репозиторию, в GitHub просто нет новых коммитов. Проверяется по дате последнего коммита в GitHub.
2. **GitHub → сервер.** Если на Beget стоит вебхук/cron с `git pull`, он мог отвалиться (сменился токен, ветка, права). Проверяется `git log -1` в каталоге проекта на сервере.
3. **Сборка на сервере.** Даже при успешном `git pull` нужен `npm ci && npm run build`; если сборка падает (например, по памяти) — nginx продолжает отдавать старый `dist`/`.output`.
4. **Перезапуск процесса.** Сайт SSR-ный (Node), поэтому после сборки процесс нужно перезапускать (pm2/systemd). Без рестарта отдаётся старый серверный бандл.
5. **Кэш nginx/CDN.** Проверяется в последнюю очередь: даже при полном кэше `sitemap.xml` обновился бы после рестарта.

## Что предлагаю сделать

1. Добавить в проект GitHub Actions workflow деплоя (`.github/workflows/deploy.yml`): сборка на CI и выкладка на сервер по SSH с перезапуском процесса — чтобы деплой перестал зависеть от ручных шагов на сервере.
2. Добавить маршрут `/api/public/version`, который отдаёт идентификатор сборки и дату — тогда после каждого деплоя можно за секунду понять, обновился ли сервер.
3. Вывести тот же идентификатор сборки в HTML-комментарий/мета-тег, чтобы «свежесть» страницы читалась прямо из ответа.

## Технические детали

- Workflow: `checkout` → `bun install --frozen-lockfile` → `bun run build` → `rsync` артефактов на сервер → рестарт (`pm2 reload` или `systemctl restart`). Секреты (`SSH_HOST`, `SSH_USER`, `SSH_KEY`, путь) задаются в GitHub Secrets — их нужно будет добавить вам.
- Маршрут версии — server route под `src/routes/api/public/`, возвращает JSON `{ commit, builtAt }` из переменных окружения сборки.

## Что нужно от вас

Чтобы точно назвать сломанное звено, нужны две вещи: дата последнего коммита в GitHub-репозитории и способ деплоя на Beget (вебхук, cron с `git pull`, ручной SSH, панель Beget). Без этого можно только заменить всю цепочку на CI-деплой по пункту 1.
