# Переход с мок-данных на PostgreSQL

Цель: авто и брони приходят из реальной базы на VPS, интерфейсы `Car` и `Booking` не меняются, логика доступности (`availability.ts`) сохраняется и работает на данных из БД. Без `DATABASE_URL` (превью Lovable) всё автоматически падает обратно на текущие моки, чтобы сайт в превью не ломался.

## Что появится

1. **Подключение к базе** — пул соединений `pg.Pool` на сервере, единый на процесс, строка подключения из `DATABASE_URL`.
2. **Серверные функции** (вызываются из страниц, SQL никогда не попадает в браузер):
   - `getCars()` — список авто
   - `getCarBySlug(slug)` — одно авто
   - `getBookings()` — брони (для админки, профиля и проверки занятости)
   - `createBooking(data)` — создание брони с проверкой пересечения дат на сервере
   - `updateBookingStatus(id, status)` — смена статуса из админки
3. **Маппинг данных**: строки таблиц `cars` / `bookings` превращаются в текущие объекты `Car` и `Booking`. Фото берутся из колонки `images` (первое фото — основное, остальные — галерея). Цена по городу — `price_city`, «за город» — `price_out`. Всё, чего нет в колонках, читается из `specs` (мощность, расход, объём, депозит, лимит пробега, топливная политика и т.п.).
4. **Экраны на реальных данных**: каталог, карточка авто, главная (гараж/популярные модели), бронирование, оплата, договор, профиль, SEO-страницы, sitemap, и вся админка (авто, брони, финансы, дашборд).
5. **Доступность**: `availability.ts` остаётся как есть по смыслу, но перестаёт сам импортировать моки — список броней передаётся в него явно (из БД). Проверка пересечений дополнительно выполняется на сервере при создании брони, чтобы двойное бронирование было невозможно.

## Технические детали

- Новые файлы:
  - `src/lib/db.server.ts` — ленивое создание `Pool` (`globalThis`-кэш, `ssl` по строке подключения), хелпер `query()`, флаг `hasDatabase()`.
  - `src/lib/carsRepo.server.ts`, `src/lib/bookingsRepo.server.ts` — SQL и мапперы строк в `Car` / `Booking`.
  - `src/lib/catalog.functions.ts`, `src/lib/bookings.functions.ts` — тонкие `createServerFn`-обёртки: только импорты и объявления функций, вся логика и `await import("./*.server")` внутри `.handler()`.
- Пакет `pg` (+ `@types/pg`) добавляется в зависимости; импорт делается динамически внутри хендлера, чтобы сборка превью (Cloudflare-режим) не тянула Node-модуль в граф.
- Фолбэк: если `process.env.DATABASE_URL` пуст — репозитории возвращают данные из `src/data/mockCars.ts` / `src/data/mockBookings.ts` (файлы остаются как fallback-датасет, компоненты их больше напрямую не импортируют).
- Загрузка данных: у страниц появляются `queryOptions` + `loader: ensureQueryData` и `useSuspenseQuery` в компоненте. Клиентские компоненты (`GarageShowcase`, `CarQuickView`, `PopularModels`, `CatalogFilters`, `AvailabilityCalendar`, `BookingHistoryList`, карточки админки) получают `cars`/`bookings` пропсами от страницы — их разметка и стили не меняются.
- Мутации: `createBooking` и `updateBookingStatus` вызываются через `useServerFn` из обработчиков, после успеха — инвалидация ключей `["cars"]` / `["bookings"]`.
- `createBooking` валидируется Zod (`carId`, `clientPhone`, `dateFrom`, `dateTo`, `total`), при отсутствии клиента по телефону создаёт запись в `clients`, статус новой брони — `pending`.
- Админ-функции (`getBookings`, `updateBookingStatus`) остаются за существующим админ-гейтом по паролю; публичные функции отдают только безопасные поля (без `plate` и данных клиентов).
- `src/lib/exportExcel.ts` и `dashboardStats` переводятся на переданные данные вместо прямого импорта моков.

## Что понадобится от вас

- Значение `DATABASE_URL` (добавляется как секрет на сервере/в окружении сборки). В превью Lovable его можно не задавать — там продолжат работать моки.
- Подтверждение, что в `cars.status` используются те же значения, что во фронте (`free` / `busy` / `washing` / `maintenance`), а в `bookings.status` — `pending` / `paid` / `active` / `completed` / `cancelled`. Если значения другие, добавлю таблицу соответствия при маппинге.
