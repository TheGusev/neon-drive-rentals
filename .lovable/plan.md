# Версионный кэш статики и «всегда свежая» страница после деплоя

Цель: после пуша в GitHub и обновления кода на сервере пользователь никогда не видит старую версию сайта — HTML всегда свежий, CSS/JS подтягиваются новые, а вкладки, открытые до деплоя, сами предлагают обновиться.

## Что сейчас

- Сборка Vite уже даёт хешированные имена файлов для JS/CSS (`app-XXXXXXXX.js`), то есть сами бандлы не «залипают» — залипает HTML-документ, который на них ссылается.
- Иконки и манифест в `public/` версионируются вручную (`?v=2`) — при каждом релизе это надо править руками.
- В репозитории нет GitHub Actions workflow: обновление на Beget идёт вне репозитория.
- Сервис-воркера нет, поэтому «вечного» офлайн-кэша PWA нет — это упрощает задачу.

## Что сделаем

1. **Идентификатор сборки**
   Ввести `BUILD_ID` (хеш коммита или таймстемп сборки), доступный и на сервере, и в клиенте. Один источник правды для заголовков, запросов иконок и проверки обновлений.

2. **Правильные заголовки кэширования**
   В серверной обёртке ответа:
   - HTML-документы — `no-cache, must-revalidate` (браузер каждый раз спрашивает сервер, но отдаёт мгновенно, если ничего не изменилось);
   - хешированные бандлы и картинки из сборки — `max-age=31536000, immutable` (кэшируются навсегда, имя меняется при изменении);
   - `manifest.webmanifest`, иконки, `robots.txt`, `sitemap.xml` — короткий кэш с ревалидацией.

3. **Версионные ссылки на нехешированную статику**
   Заменить ручной `?v=2` у favicon / apple-touch-icon / манифеста на `?v={BUILD_ID}` — новые иконки и манифест подхватываются автоматически на каждом релизе.

4. **Эндпоинт версии + мягкое авто-обновление**
   - Публичный маршрут `/api/public/version`, отдающий текущий `BUILD_ID` с `no-store`.
   - Небольшой клиентский хук: при возврате на вкладку и раз в несколько минут сверяет версию. Если на сервере новее — показывает ненавязчивый тост «Вышло обновление сайта — Обновить», по клику перезагружает страницу. Никаких принудительных перезагрузок посреди оформления брони.

5. **Инструкция для Beget (`DEPLOY.md`)**
   Готовый фрагмент конфигурации nginx: не кэшировать HTML на уровне прокси, отдавать `immutable` для директории сборки, плюс порядок деплоя (pull → build → перезапуск Node-процесса), чтобы старый процесс не продолжал отдавать старую сборку.

## Проверка

- Прод-сборка локально: проверяю заголовки ответа для главной, для хешированного `.js/.css`, для манифеста и иконок.
- Сценарий «пользователь со старой вкладкой»: открываю страницу, подменяю версию на сервере, убеждаюсь, что появляется предложение обновиться и после перезагрузки грузятся новые файлы.
- Проверяю, что имена бандлов действительно меняются между двумя сборками при изменении кода.

## Технические детали

- `BUILD_ID` пробрасывается через `define` в `vite.config.ts` (значение — `GITHUB_SHA`, если есть, иначе таймстемп сборки), плюс тонкий модуль `src/lib/build-version.ts` для типизированного доступа.
- Заголовки навешиваются в `src/server.ts` поверх ответа `@tanstack/react-start/server-entry` — существующая обработка ошибок SSR сохраняется.
- Маршрут версии — `src/routes/api/public/version.ts` (префикс `/api/public/` не требует авторизации), только чтение константы, без данных пользователя.
- Хук обновления монтируется один раз в `src/routes/__root.tsx`, использует уже подключённый `sonner` для тоста.
